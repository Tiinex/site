# Cold-Start Grounding And Handoff Trust — Anchor Discovery

## Discovery Intent

- Intent: qualify the current cold-start grounding, Handoff, carrier-profile, work-provenance, provider-default, and multi-route seams before delegating Major 009 implementation.
- Starting Question: what already works generically, what is merely Tiinex dogfood convention, and which remaining gaps require canonical semantics rather than mechanical repair?

## Discovery Field

- Field: carried Major-009 Business, Docs, and Site source plus current portable Tooling implementation and permanent regressions.
- In Scope: Business cold-start outcome context, Site grounding-readiness and Handoff manufacture mechanics, Docs Relation/Role/Root semantics, carried multi-route behavior, Major carrier profiles, provider defaults, and return sibling allocation.
- Out Of Scope: lifecycle/readiness Major, destructive Reduction apply, broad schema scaling, Viewer PoC parity, Pages deployment repair, remote mutation, or invention of new canonical relation vocabulary by Anchor.

## Discovery Method

- Method: use qualified carried source and Tiinex-first Tooling orientation/grounding where semantic state is involved; inspect implementation and permanent tests for mechanical behavior; compare explicit Business outcome context with actual cross-workspace graph connectivity; separate observed implementation from inferred product intent.

## Discovery Boundaries

- Boundary: Parent remains direct artifact continuity and must not be broadened into generic work or organizational ancestry.
- Boundary: Tiinex-specific names and current Foundation topology are dogfood data only; generic Tooling may not require them.
- Boundary: a prose dependency/reference is not automatically a typed work-provenance edge.
- Boundary: this Discovery does not authorize a new Relation predicate, Role authority rule, provider default, sibling allocation rule, or remote change.

## Discovery Outcome

- Outcome: completed bounded discovery with one genuine semantic gap and several independently mechanical/genericity seams.

### Finding — continuity qualification is stronger than cold-start meaning projection

- Current grounding already resolves exact selected Handoff authority, Required Context closure, complete carried Workspaces, cold-start root continuity, current-task candidates/frontier, blockers, and holder-role binding.
- The normal compact path intentionally projects Required Context pointers/counts rather than semantic body reductions; exact bodies require explicit expansion flags.
- This preserves token efficiency but leaves a cold recipient with substantially less orienting meaning than Tooling has already qualified. The current session required human narration plus manual navigation before Anchor could recover Major, frontier rationale, adjacent exclusions, organizational context, and carried-versus-remote meaning.
- Repair target should therefore be a bounded semantic grounding projection, not an unconditional dump of every Required Context body.

### Finding — organizational cold-start outcome exists but technical work provenance is not first-class

- Business carries `Portable Handoff, Cold-Start And LLM Ingress` under the Tiinex Tooling Project as explicit organizational work.
- The current Site Major-009 Task is materially about that outcome, but the Business task has no descended technical work in its Parent lineage and Site references are prose/dependency/context references rather than a qualified typed work-provenance graph edge.
- Docs `tiinex.relation.v1` explicitly keeps Parent narrow and allows ordinary artifacts or schema contracts to declare/project typed non-Parent edges.
- No current canonical generic relation vocabulary was found that says a technical lineage implements, is spawned by, serves, or is controlled by an Initiative/Epic/outcome/task context. Anchor must not invent that predicate.
- Until canonical semantics exist, grounding should report organizational work provenance as unresolved rather than infer it from filenames, folders, summaries, repository placement, or prose dependencies.

### Finding — project/carrier Major profile is partly hard-coded as Tiinex Foundation

- `carrierLineage.js` and the recipient-v2 package contract currently embed `business`, `docs`, and `site` as Major closure requirements.
- The Tiinex Foundation requirement itself is legitimate project policy, but it is located inside generic Tooling instead of a declared project/carrier profile or explicit operator input.
- Mechanical repair can separate generic complete-workspace policy from the Tiinex Foundation profile without changing current Tiinex behavior.

### Finding — schema provider defaults mix generic operation with bundled Tiinex profile

- CLI schema-resolution paths currently default to repository `Tiinex/docs` and ref `master` when not explicitly supplied.
- A bundled Tiinex canonical pack/profile is legitimate; treating those values as universal provider semantics is not.
- Repair should make provider selection/profile provenance explicit while preserving current Tiinex dogfood convenience.

### Finding — shared multi-route carrier semantics are already real

- Current manufacture supports one carrier containing multiple qualified Handoff routes and cold consumers must select exactly one route; sibling-route inference is forbidden.
- Carrier filename projection can represent multiple recipients and remains non-authoritative.
- Human ergonomics remain incomplete because ordinary manufacture/output normally presents one selected route's exact transport text at a time rather than a first-class `one ZIP + N route texts` projection.

### Finding — return sibling numbering is manufacture-order today

- Parallel non-major returns reserve a local sibling index atomically from the parent package; first manufactured return receives `-1`, second `-2`, independent of original route order.
- Mapping original Handoff Pointer order to return dimensions would improve deterministic human progress projection, but retry/divergence/collision behavior must be reconciled before changing it.
- No implementation change should be made merely for cosmetic numbering.

### Finding — semantic and mechanical delegation can be split safely

- Axiom is needed for the generic work-provenance/organizational relation contract and any participant-input/authority semantic clarification that existing schemas do not already settle.
- Loom can proceed in parallel on bounded mechanics that do not depend on that semantic result: grounding-capsule projection scaffolding, Required Context reductions over already-qualified material, generic carrier/profile separation, explicit provider-profile boundaries, multi-route transport-text projection, and tests.
- Loom must leave organizational work-provenance relation interpretation fail-visible/unresolved until Axiom returns.

## Relation Candidates

- Candidate: a typed non-Parent relation from a technical work root (or its work-spawning Handoff) to the controlling organizational work artifact, traversable upward and downward without copying technical task trees into Business.
- Candidate boundary: the relation should answer why work exists / which outcome caused it, while Parent continues to answer direct artifact continuity.
- Candidate status: semantic authority unresolved; requires Axiom disposition before implementation.

## Next Artifacts

- Handoff to Axiom: reconcile generic work-provenance and organizational-context relation semantics, plus any relevant participant-input authority boundary.
- Handoff to Loom: implement only semantics-independent grounding/Handoff genericity mechanics and regressions; preserve an explicit unresolved hook for Axiom-owned work-provenance semantics.
- Anchor reconciliation after both returns: integrate without making either specialist authoritative over the other's domain.

## Interpretation Limits

- Limits: this Discovery does not prove that all existing technical lineages lack organizational provenance, that every technical artifact needs a direct Business relation, that Relation Artifacts are mandatory intermediates, or that original pointer-order sibling numbering is semantically correct.
- Limits: it does not authorize broad schema changes, lifecycle/reduction work, Viewer parity work, or remote mutation.
- Limits: the observed Tiinex Business task and current role names are dogfood evidence, not generic Tooling vocabulary.
