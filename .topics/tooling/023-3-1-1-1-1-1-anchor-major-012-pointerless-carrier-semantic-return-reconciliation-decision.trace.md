# Major 012 Pointerless Carrier Semantic Return — Anchor Reconciliation

Anchor accepts Axiom's corrected two-mode carrier disposition as the semantic boundary for the final bounded Major 012 implementation follow-through. Existing exact-Handoff-route behavior stays unchanged; pointerless Workspace transport is explicit, non-Handoff transport only.

## Decision

- State: accepted-for-implementation
- Subject: Axiom return for `No Handoff pointer` semantics inside Major 012
- Decision: accept the exact `tiinex.handoff.package.v1` two-mode disposition from `023-3-1-1-axiom-pointerless-handoff-carrier-mode-semantics-decision.trace.md` and route Loom to implement the shared Tooling and thin VS Code operator surfaces against that disposition. `recipient-facing-handoff-carrier` retains the current exact selected-Handoff route. `recipient-facing-workspace-carrier` uses the exact all-`none` Route Discovery triplet and carries no Handoff endpoint, transfer, Required Context, recipient-role, current-work, or completion semantics.
- Operative Effect: Loom may implement only the returned two-mode semantics plus the already accepted Major 012 human-operator requirements. Pointerless package manufacture must remain fail-closed until the maintained canonical Docs contract also accepts the mode.

## Basis

- The repaired Axiom return now resolves explicit durable Axiom and Anchor Role endpoint references, and the exact return carrier grounds to act under an explicit Anchor holder-role binding.
- The returned semantic delta is backward-compatible: existing Handoff carriers remain valid and exact-route qualification is not weakened.
- The pointerless mode preserves the architectural boundary that package transport owns carrier discovery/Workspace snapshot binding while `tiinex.handoff.v1` alone owns From/To, Transfers, Required Context, retained responsibility, and completion-facing semantics.
- The returned UI boundary matches the accepted operator requirement: only qualified Handoff leaves are eligible route candidates, `No Handoff pointer` is always a deliberate Workspace-transport choice, and Workspace inclusion does not select or infer a Handoff.
- The previous Loom return is already accepted as a qualified implementation foundation, but it intentionally predates the later Sigma acceptance refinements and therefore is not yet sufficient for human dogfood.

## Consequences

- Loom receives one final bounded implementation tranche over current shared Site Tooling and `Tiinex/vscode`.
- The tranche must complete the accepted native operator surface: validator-driven diagnostics, deterministic hygiene Quick Fixes, conservative Handoff discovery/settings, branch-safe landing, after-landing commit/push policies, selected-Handoff opening, native Handoff authoring, and native package manufacture/preview without tasks.json or manual operator scripts.
- Native Handoff creation must consume the same schema creation/authoring/validation/integrity semantics as shared Tiinex Tooling. The VS Code extension owns form/UI behavior only and must not create an alternate Handoff authoring grammar.
- Native package creation must consume shared manufacture logic. VS Code may choose a qualified Handoff leaf or explicit `No Handoff pointer`, choose included Workspaces, and expose only exclusion choices that preserve the qualified complete-Workspace snapshot boundary; it must not hand-roll ZIP or route semantics.
- The maintained Docs `tiinex.handoff.package.v1` text still requires canonical follow-through for the accepted two-mode delta. That remains an Axiom-owned semantic materialization step after Loom implementation qualification unless Loom returns a concrete contradiction requiring earlier semantic review.
- Sigma dogfood and Major 012 closure remain blocked until Anchor reconciles the returned implementation, canonical follow-through is qualified, and one installable native VSIX is ready for bounded human observation.

## Review Conditions

- Return to Axiom before implementation completion only if Loom finds a concrete semantic contradiction with the exact two-mode decision.
- Do not broaden this utility Major into general Viewer replacement, migration of the old provenance extension, broad artifact-studio work, destructive Reduction apply, deployment/release, or Foundation exit.
