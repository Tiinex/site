# Safe Reduction And Shared Capability Parity

## Objective

Replace the current broad Site-reduction execution frontier with a fail-closed reduction-safety and shared-capability-parity frontier. No historical artifact is physically removed until canonical Reduction semantics and shared Tooling can prove, before deletion, the complete set of disappearing semantic leaves, every immutable expansion reference, the collapse boundary, and the recoverable leaf-to-boundary lineage span, including when that boundary crosses repository/workspace scope. In parallel, harden audit/repair and transport grounding so Viewer humans and LLM consumers operate the same shared mechanics rather than separate policy implementations.

## Done Criteria

- The previously prepared broad reduction candidate is treated as non-authoritative experiment/evidence only and must not be landed merely because its tests passed.
- Destructive reduction is fail-closed unless a qualified Reduction artifact already exists before the destructive diff and names every semantic leaf whose current material will disappear.
- Every disappearing semantic leaf has an immutable commit-pinned repository/path permalink, explicit disposition/reason, and an explicit surviving collapse boundary.
- For every disappearing leaf, Tooling can prove the complete declared Parent span from that leaf to the surviving collapse boundary using immutable material; shared ancestors may be represented once without losing per-leaf reachability.
- The collapse boundary may cross Site/Docs/Business workspace or repository boundaries when that is the nearest truthful surviving semantic ancestor; repository boundaries must not force an artificial Site-local anchor.
- Active, unresolved, disputed, unaccepted, or fixture-required branches fail reduction eligibility unless they are truthfully retained or reissued under a current qualified ancestor.
- Reduction planning distinguishes semantic leaves from transport-only/package artifacts and fixtures, and reports ambiguous classification instead of guessing.
- Axiom returns canonical semantic disposition for Reduction-before-delete, leaf-to-cut closure, immutable references, cross-repository placement, and whether `tiinex.reduction.v1` or adjacent canonical contracts require change.
- Loom inventories the existing shared `audit`, `repair-plan`, `lineage-integrity-plan`, `lineage-integrity-project`, and `lineage-integrity-apply` mechanics before adding new behavior; missing capability is filled in shared Tooling rather than privately in Viewer.
- Shared audit can flag broken artifacts and broken lineages with stable machine-readable finding codes, severity, ownership/boundary guidance, and enough identity to locate affected artifacts.
- Shared repair tooling can project bounded repair actions, preserve unknown content and provenance/continuity boundaries, require explicit approval for mutating local material, produce a changeset/receipt, and re-audit repaired results without remote writes.
- Batch/repository-scale repair planning groups repeated defects without hiding per-artifact findings or lineage cascade effects.
- Viewer can consume the same shared audit/repair capability model and action implementations so human and LLM surfaces have 1:1 semantic capability parity; Viewer may add presentation but not fork repair policy.
- Shared Handoff carriers can carry multiple qualified sibling routes in one exact ZIP while recipient-specific transport text selects one route explicitly; package consumption never assigns a session role by implication.
- Cold grounding exposes sender role, recipient role, selected route, and explicit session/holder binding state; absence of a holder binding remains unresolved rather than mapping recipient to assistant/user by guess.
- A later reduction execution task is created only after Axiom semantic return and Loom qualification prove the above gates on the unreduced Site graph.

## Scope

- Site reduction preconditions, expansion/recovery proof, and cross-repository collapse-boundary architecture.
- Shared Tooling audit/repair inspection, planning, local application, receipts, re-audit, and batch/lineage coverage.
- Shared capability projection needed for Viewer human/LLM parity.
- Multi-route Handoff carrier selection and role/actor grounding semantics at the Tooling boundary.
- Additive Tasks/Handoffs/Evidence only during this coordination tranche; no historical trace deletion.

Out of scope: physically reducing Site history in this tranche; rewriting historical artifact bytes; Playthings Verse/world semantics; merging the `playthings` branch; remote repository mutation by Anchor; Viewer product acceptance; using package membership or filename conventions as role assignment.
