# Sigma Cross-Repository Work Provenance And Cold-Start Organization Context Feedback

## Observed Signal

- Sigma observed in the Playthings spatial lineage view that technically valid Site lineages can appear disconnected from the higher-level Business/organizational work that caused them to exist.
- The same gap would be unfair to a cold-started LLM: valid Parent continuity alone may not explain why the work exists, which Initiative/Epic/outcome controls it, or which organization/project context it belongs to.
- Sigma's input is feedback/observation by default, not an automatic acceptance, priority, or semantic authority transition.

## Source

- Source: direct Sigma observation and discussion with Anchor during Major 008 on 2026-09-05, using Playthings lineage visualization as human evidence of discoverability/framing friction.
- Context: carried Business/Docs/Site Foundation work and the already approved future Grounding + Handoff Trust / Architecture plan.

## Interpretation

- Parent should remain artifact continuity and must not be overloaded merely to force every technical artifact under a Business or organization root.
- Work provenance / controlling-work context should remain explicitly traversable from technical work toward the higher-level work/outcome that caused it when qualified evidence exists.
- Organization/project context is a distinct grounding concern: a cold consumer should be able to understand the declared project/organization world the work belongs to or crosses without inferring from repository names, folders, branches, or nearby artifacts.
- Generic Tooling must remain domain-neutral; Tiinex, Business, Sigma, Anchor, particular repositories, and particular planning nouns are project data rather than hardcoded runtime semantics.

## Feedback Target

- Target: the approved post-Major-008 Grounding + Handoff Trust major, later Architecture/Scale audit, and any existing Relation/Handoff/Discovery mechanisms used to express cross-repository work provenance.

## Feedback Received

- Preserve discoveryable upward/downward connection between higher-level work and technical execution without duplicating technical task trees into Business.
- A future cold-start grounding projection should, when evidence exists, answer: what local lineage this belongs to; what higher-level work caused it; which workspace/repository owns execution; which project/organization context is declared; and whether the relation can also be discovered downward from the controlling work.
- If organizational work provenance is not qualified, expose it as unresolved rather than guess.

## Disposition

- State: carried-forward planning feedback.
- Follow-Up: Anchor should reconcile this requirement during the already approved Grounding + Handoff Trust and Architecture/Scale majors; no representation/schema decision is made by this feedback.
- Major 008 is not broadened by this observation.

## Limits

- This feedback does not decide canonical Relation semantics, require Business to become Parent of technical artifacts, authorize duplicate task trees, hardcode any Tiinex role/repository name, or claim that every currently disconnected visual lineage is semantically defective.
- Playthings is evidence/donor presentation only and is not authority over refactor semantics.
