# Anchor Artifact-First Phase 1 Detached Cache And Participant Role Acceptance

## Decision

- State: accepted
- Subject: artifact-first Phase 1 detached-cache External Payload ownership and selected-route participant Role transport/grounding
- Decision: accept the exact bounded Loom return in `004-loom-to-anchor-artifact-first-phase1-cache-role-handoff.trace.md` as qualified Phase 1 implementation evidence. Detached-cache ownership, cache-backed Required Context closure, selected-route participant Role Pointer transport/grounding, and compatibility non-authority are accepted within the stated subset. Phase 2 omission/default transition remains separately gated until the two disclosed broad handoff-suite losses are reconciled enough to establish a trustworthy baseline. Broader binary payload coverage remains separate and is not accepted by this decision.

## Basis

- Tiinex cold-start qualification of the received carrier passed the preferred routed-package path and qualified all three declared Required Context files from exact carried Workspace bytes.
- The exact carried Site Workspace archive independently matched its declared SHA-256 before audit materialization.
- `node src/tooling/portable/handoff/recipientV2.artifactFirstPhase1.nextSubset.test.mjs` passed on the exact carried Workspace.
- `node src/tooling/portable/handoff/recipientV2.artifactFirstPhase1.test.mjs` also passed, preserving the predecessor Phase 1 dual-projection seam.
- Source audit confirmed that selected-route detached material is projected into a visible Workspace-scoped `tiinex.external.payload.v1` cache with exact ZIP identity and explicit material-to-entry bindings; Required Context resolution uses exact Workspace/cache bytes rather than compatibility JSON.
- Source audit confirmed that selected-route participant Role Pointers bind exact Workspace/cache entries, require `tiinex.party.role.v1` plus visible Role Label agreement, and do not infer holder identity or change Handoff From/To authority.
- Semantic-only Phase 1 inspection remains independently qualified without the compatibility transport JSON; Phase 1 interoperability still retains that JSON as derived output.
- The two broad-suite losses disclosed by Loom were independently reproduced with the same observed symptoms: `carrierProjection.test.mjs` sees `blocked` where its legacy fixture expects `ready`, and `coldConsumerEntrypoint.test.mjs` observes projected carrier dimension `001` where the legacy expectation is `005`.

## Consequences

- The named detached-cache and participant-role Phase 1 subset may be treated as accepted local Site implementation evidence.
- This is not broad release acceptance, broader binary coverage, Viewer acceptance, canonical Docs schema mutation, or Phase 2 authorization.
- The next bounded Loom tranche should reconcile only the two named broad-suite losses before Anchor decides whether the clean-carrier Phase 2 default transition has a sufficiently trustworthy baseline.
- Reconciliation should determine whether each loss is a stale legacy expectation or an implementation defect, repair only what qualified current semantics require, and return rather than inventing new carrier semantics if authority is insufficient.
- Accepted Phase 1 focused/predecessor behavior must remain green through that reconciliation.

## Review Conditions

- Reopen this acceptance if either named broad-suite reconciliation demonstrates that the accepted Phase 1 subset caused an unrecognized semantic regression.
- Reopen before Phase 2 if compatibility omission exposes receiver truth still dependent on derived transport JSON.
- Broader binary payload coverage should be authorized independently when a concrete requirement justifies it rather than being folded into the baseline repair by scope drift.
