- State: accepted
- Subject: first shared Operating Overview Tooling projection and next source-identity frontier
- Decision: accept Loom's `031-loom-to-anchor-operating-overview-tooling-projection.trace.md` as the first qualified provider-neutral Operating Overview Tooling slice. `project-operating-overview` may project already-loaded Project inventory, exact-qualified declared-current Task candidates, explicit blocker/resource signals, and already-loaded Monitoring/Source/Relation/Workspace declarations without becoming semantic authority. Monitoring freshness and remote cross-repository traversal remain explicitly deferred.

## Accepted Semantic Boundary

- Axiom's prior disposition remains controlling: no Dashboard, Status, Initiative, Epic, or Frontier semantic schema is justified by this requirement.
- The overview is projection-only. Project, Task, Handoff, Decision, Monitoring, Source, Resource, Signal, Relation, Workspace, Pointer, and Discovery artifacts retain their own truth.
- A lineage leaf is not a workflow frontier; Task lifecycle state is not lineage position.
- Monitoring declarations may be surfaced when loaded, but freshness is not inferred from host time, network state, or absence of change.
- Cross-repository declarations may be surfaced when loaded, but remote traversal is not inferred or silently performed.

## Post-Acceptance Discovery

- Anchor independently exercised `project-operating-overview` with more than one already-loaded input root. The current CLI loader already accepts multiple explicit targets and merges their loaded material; a new multi-root overview loader is therefore not justified.
- That proof also exposed the next concrete gap: target-local relative paths and a generic `portable-node-local` source mode are insufficient to distinguish same-path records from different loaded roots, and text records currently lose the node-file/node-zip locator detail already retained for some asset material.
- This is a source/projection identity gap, not a schema-authority gap and not permission to infer GitHub provenance.

## Next Tooling Authorization

- Inspect existing portable input/source/locator contracts before adding any new abstraction.
- Preserve explicit loaded-source identity for text records across file, directory, ZIP, and multiple-target input without changing authored artifact identity or inferring repository provenance.
- Expose only the smallest non-authoritative source/locator basis needed for Operating Overview consumers to distinguish otherwise-colliding loaded records and understand where supplied material came from.
- Prefer reusing current node-file/node-zip locator shapes or existing explicit source metadata. Do not turn local paths into public permalinks or claim repository identity unless separately supplied and qualified.
- Add focused adversarial proof with at least two loaded roots that contain the same relative artifact path but remain distinguishable by explicit material-source/locator basis.
- Preserve the accepted Operating Overview semantics and all 21 portable Handoff tests.

## Stop Conditions

- Stop before changing canonical Source, Workspace, Project, Task, Relation, Monitoring, Parent, or provenance semantics.
- Stop before inventing GitHub/repository identity from local filesystem placement.
- Stop before remote traversal, Viewer integration, Business mutation, Docs mutation, or general lineage identity redesign.
- Return to Anchor/Axiom if the smallest truthful locator/source basis requires a new semantic contract rather than Tooling projection metadata.
