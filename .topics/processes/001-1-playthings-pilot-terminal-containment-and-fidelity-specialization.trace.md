# Playthings Pilot Terminal Containment And Fidelity Specialization

## Terminal Completion Rule

For Playthings visual generation executed through Pilot, the bounded execution is terminal once the returned source is preserved, execution Evidence is authored, the Pilot-to-return-role Handoff is authored, and the required return package is manufactured. After that point Pilot performs no exploratory or interpretive workspace work. It does not inspect ambient README, validation, schema, adapter, or Tooling implementation material merely because those files remain carried in the workspace.

If return-package manufacture is blocked before a package exists, Pilot records the blocker and returns blocked according to the controlling execution contract. It does not inspect implementation internals unless that diagnostic work was explicitly delegated as a separate Task.

## Active Context Narrowing

After recipient grounding, active execution context is the controlling Task/Handoff, Pilot Role, declared execution process, ordered manifest, exact execution request, declared authority inputs, returned execution material, and the minimum Tooling interface required to validate/materialize Evidence and return Handoff. Other carried workspace prose is ambient context rather than active task authority unless explicitly referenced by the controlling work.

## Execution Boundary Supremacy

When the controlling Task/Handoff declares that the delegated action is human-mediated, that declaration outranks Pilot's available runtime tools. Pilot must not directly perform, simulate, or substitute the delegated external action even when an apparently equivalent image-generation, browser, app, coding, or other execution tool is available in Pilot's own context. Direct tool capability does not silently rewrite the declared execution boundary.

For a human-mediated visual generation Task, Pilot's execution work is limited to grounding, verifying the declared materials, presenting the exact attachment order and human-visible input, bounded clarification, receiving the returned result, evidence capture, and return manufacture. Pilot does not invoke image-generation itself unless a separate controlling artifact explicitly changes the execution boundary.

## Mandatory Human Wait State

After Pilot presents the decision-minimal human execution instructions, Pilot enters an explicit `awaiting-human-execution-result` state. While in that state:

- Pilot does not call any tool that performs or approximates the delegated external action;
- Pilot does not generate replacement outputs, previews, or substitute evidence;
- Pilot may only answer bounded clarification about the already-issued human instructions or receive the returned result/control signal;
- absence of a returned result is not permission to continue autonomously.

The wait state ends only when the human returns the requested result, reports a bounded blocker/deviation, or a new controlling artifact explicitly changes the task.

## Fidelity Classification

Visual execution evidence distinguishes at least these layers when observable:

- exact-byte match;
- byte mismatch with decoded pixel-equivalence;
- decoded-pixel mismatch whose semantic effect is not yet reviewed;
- material semantic/visual deviation;
- provider/host internals unavailable.

A PNG whose bytes differ but whose decoded RGBA pixels are identical is not silently called an exact-byte match and is not escalated into a semantic visual mismatch. The Evidence records both facts. Provider/host cause remains unknown unless directly evidenced.

## Interpretation Limits

- Does Not Mean: Pilot may self-review the generated visual, full workspaces are forbidden in Handoff carriers, byte-equivalence can be inferred without comparison, or ambient repository documentation loses its authority for other Tasks.
- Must Not Be Used To Claim: implementation-level root cause without direct evidence, visual acceptance from transport checks, or permission for Pilot to continue after terminal return-package completion.
