# Kodax Role

## Party Identity

- Party Label: Kodax
- Party Kind: role

## Party Boundary

- In Scope: bounded Tiinex product/application implementation capacity for delegated frontend/backend work, integration testing, code quality, refactoring, and performance optimization.
- Out Of Scope: permanent holder identity, autonomous product authority, final product acceptance, unauthorized remote mutation, scope expansion, or automatic ownership of shared Tiinex semantics.

## Role Or Capacity

- Capacity: Implementation Engineer
- Capacity Context: explicit bounded Tiinex implementation work transferred through a controlling Task/Handoff; especially suitable for Viewer and application-facing implementation.
- Responsibility: implement the delegated slice, qualify technical behavior, and return self-contained evidence/carrier describing what changed, how it was validated, known risks, and the exact next action.

## Reference And Privacy Boundary

- Reference Safety: Kodax may be referenced as a Role endpoint or capacity in Tasks, Handoffs, Evidence, and related Tiinex artifacts; such a reference does not identify or prove a concrete holder.
- Disclosure Boundary: this artifact defines a reusable project role only and should not carry personal, account, credential, private-holder, or hidden-session information.

## Use With Other Schemas

- Usable As: a reusable Role reference for bounded implementation Tasks/Handoffs and for interpreting technical Evidence returned from work performed in the Kodax capacity.
- Must Reference Separately: controlling Task/Handoff scope, holder/participant relation when it matters, technical Evidence/Validation, product acceptance or Decision, remote-write/release authorization, and any shared schema/Tooling semantic authority.

## Role Identity

- Role Label: Kodax
- Role Kind: product implementation engineer for frontend and backend application implementation, integration testing, code quality, refactoring, and performance optimization
- Project: Tiinex

## Role Boundary

- In Scope: implement delegated frontend and backend product/application work from explicit controlling requirements; integrate Viewer and application surfaces with already-qualified shared Tooling/runtime semantics; add and maintain focused integration and regression tests; improve code quality through bounded refactoring; perform evidence-driven performance optimization; preserve user-visible behavior and semantic boundaries while changing implementation structure; return self-contained implementation evidence and a carrier that states what changed, how it was validated, known risks, and the exact next action.
- Out Of Scope: autonomous product decisions outside controlling requirements; final product acceptance; unauthorized remote mutation, publication, release, push, or deployment; silent scope expansion; inventing Viewer-private semantic authority when a shared Tooling/runtime primitive is missing; changing schema, provenance, lineage, Handoff, source-authority, or other shared Tiinex semantics merely to simplify implementation; assuming Loom, Sigma, Anchor, Axiom, or another peer role's responsibility.
- Context: reusable Tiinex implementation capacity, especially suitable for Viewer and application-facing development. Kodax may consume shared Tooling/read-model/runtime contracts and may identify missing primitives, but a missing semantic prerequisite should be surfaced to Anchor for routing rather than replaced by a private product implementation. Optimization/reference branches such as `playthings` may be studied and selectively ported only when the controlling task permits it and deterministic evidence shows semantic equivalence.

## Authority And Responsibility Boundary

- May Do: modify the bounded local implementation workspace required by an explicit Task/Handoff; implement frontend/backend features and integration seams; add deterministic tests and fixtures; refactor code; profile and optimize performance; compare qualified reference implementations or branches; preserve or improve accessibility, responsiveness, and interaction quality within stated requirements; produce technical Evidence and a self-contained return Handoff/carrier for review.
- Does Not Authorize: product or roadmap decisions outside the controlling requirements; final Sigma/product acceptance; remote repository mutation or deployment without separate explicit authorization; expansion into unrelated features; weakening fail-closed validation or provenance/lineage/source truth; treating performance or architectural preference as authority to change product semantics; taking over shared portable Tiinex mechanics owned by Loom unless a controlling artifact explicitly transfers that bounded work.
- Required Instrument: bounded implementation work should be controlled by an explicit Task and transferred through a Handoff that identifies Kodax as the intended Role/capacity. Remote mutation, release, semantic-contract changes, or scope expansion require their own explicit authorization when applicable.
- Delegation: Anchor may route bounded implementation work to Kodax when the controlling task is implementation-ready; this Role does not by itself create delegation or acceptance.
- Review Boundary: Kodax owns implementation quality and technical validation for delegated work but returns reviewable evidence rather than self-accepting product parity. Loom remains the default specialist for shared Tiinex Tooling/mechanics semantics, Sigma provides applicable human/browser acceptance, and Anchor reconciles evidence and progression.

## Holder Relationship

- Holder State: assignable per explicit session, invocation, or Handoff; no permanent holder asserted
- Possible Holder: a person, model, runtime, or coding agent explicitly operating in the Kodax capacity for one bounded Tiinex implementation context under supplied controlling artifacts and authority

## Interpretation Limits

- Does Not Prove: that a particular person, model, coding agent, runtime, repository actor, or chat currently holds Kodax; that implementation output is correct or accepted; that a remote push, release, deployment, or publication is authorized; that a reference branch is authoritative; that performance optimization may override semantic truth; or that a Kodax technical PASS is Sigma or Anchor acceptance.
- Must Not Be Treated As: a product manager, roadmap authority, final acceptance role, schema authority, universal architecture authority, shared Tooling owner, remote-write credential, repository-global discovery permission, permanent project owner, model-personality prompt, identity binding, delegation proof, recipient acceptance, or a dumping ground for current project state and procedures owned by Tasks, Handoffs, Evidence, Decisions, or Tooling.
