# Complete Root Named Companion Suite

## Objective

Make Root the first complete integration fallback:

```text
root.playthings.character.png
root.playthings.verb.png
root.playthings.blueprint.png
root.playthings.portrait.png
root.playthings.tiles.png
root.playthings.props.png
```

Then use those six channels to qualify independent exact→Parent→Root resolution and prepare the first dynamic Place/multi-floor runtime test.

## Current Integration Seeds

- `root.playthings.character.png` is initially a deterministic byte-copy of the accepted Sigma Character v1 mobile-quality sheet. This is an integration fallback, not a claim that Root semantically is Sigma.
- `root.playthings.blueprint.png` is initially a deterministic compact derivative of the accepted Schema Module blueprint seed.
- Root Verb, Portrait, Tiles, and Props require fresh bounded Pilot generation and Anchor/Sigma review before they become accepted Root integration assets.

## Creative Routes

Four sibling Pilot routes may execute independently from this Task:

1. Root Verb — neutral inspect/observe eight-frame choreography using the current fallback character identity.
2. Root Portrait — animated steampunk Root Gate identity/state row.
3. Root Tiles — one complete 8×8 authoring family matching the accepted Tiles slot contract, later deterministically reduced to 32×32 runtime cells.
4. Root Props — one generic Root/world persistent prop row using the fixed eight-state Props grammar.

All four routes are intended for one shared multi-route Handoff package and four separate transport texts.

## Production Constraints

- Named filenames retain `.playthings.`.
- Creative source generation must leave clear separation between authored frames/cells; neighboring content must not touch or overlap.
- Pilot must show the exact generation request in one fenced Markdown code block and `continue to return` in its own fenced Markdown code block before generation.
- `continue to return` is a terminal dispatch instruction: Pilot must not invoke image generation after receiving it.
- Pilot-side substitution for the human-mediated external generation remains a process deviation and must be recorded truthfully if it occurs.
- Anchor retains source-fidelity normalization, runtime downscale, visual/technical review, acceptance, and resolver integration.
- No per-schema Playthings JSON/Markdown companion is introduced.

## Scope

- Root named-companion production and integration fallback only.
- Fresh creative generation is limited to Root Verb, Portrait, Tiles, and Props.
- Root Character and Blueprint begin as deterministic integration seeds derived from already accepted Playthings visual authorities.
- Broad schema override production, production release qualification, and generic runtime refactoring remain outside this Task until Root integration is accepted.

## Dependencies

- [Playthings Named Sheet Companion Contract](../001-playthings-named-sheet-companion-contract-decision.trace.md).
- [Playthings Tiles Dynamic Family Template](../001-1-playthings-tiles-dynamic-family-template-decision.trace.md).
- Accepted Sigma Character v1 runtime-quality sheet as temporary Root Character integration seed.
- Accepted Task/work Verb seed, Workspace place seed, and Schema Module Blueprint seed as bounded style/recovery authorities.
- Generic Business Pilot Role and Human-Mediated External Execution process for fresh external generations.
- Existing post-revert Playthings runtime baseline remains the implementation authority; historical rejected Tiles runtime code is not restored wholesale.

## Done Criteria

- all six Root named PNG channels exist as reviewed runtime-quality assets;
- Root Tiles is exactly 256 px wide and uses at least one valid 256 px-high family block;
- Root Props has fixed eight columns and at least one row;
- Root Portrait, Verb, and Blueprint each follow their fixed eight-column temporal/state template;
- Root Character follows the accepted 8×8 Character template;
- a later runtime integration descendant proves each channel can resolve independently exact→Parent→Root;
- dynamic Place testing exercises floors, walls, doorways, stairs, roof visibility/cutaway, and multiple floors from Tiles rather than separate world/local-map artwork.
