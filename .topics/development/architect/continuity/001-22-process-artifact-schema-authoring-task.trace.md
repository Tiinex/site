# Process artifact schema authoring

## Objective

Recover the intended current Tiinex/docs authoring source/base explicitly, then author and validate the minimal canonical Process artifact/schema warranted by the accepted semantic classification. The schema must own only reusable qualified composition/scope, explicit boundary exposure/binding, reusable contract/binding distinction, extraction provenance, and interpretation limits that are not already owned by existing canonical artifacts or relations.

## Done Criteria

- Before editing, recover and record the exact Tiinex/docs source identity and intended authoring base. Do not infer authority from a host/default branch, from package-local Site bytes, or from whichever remote path is easiest to access. If exact authoring authority or write surface is unavailable/ambiguous, return a blocker rather than guessing.
- Reconcile the accepted classification with current canonical Root, Relation, Transition Definition, Task, Handoff, Project, Semantic Package, and other directly relevant schema authority at the recovered authoring base. If materially stronger/newer authority contradicts the accepted classification, stop schema mutation and return the exact contradiction for Anchor disposition.
- Decide and document the exact Process schema identifier/path and author the human-readable canonical schema contract using existing Tiinex schema conventions, Root envelope/integrity rules, validation-friendly structure, and artifact creation contract expectations.
- Define Process identity/purpose and semantic boundary without redefining Project coordination, Task work units, Handoff transfer, package containment, Parent ancestry, execution order, graph adjacency, or runtime orchestration.
- Define qualified composition-member declarations that may reference genuine Tiinex artifacts, semantic roles/requirements, Transition Definitions, and typed relations while leaving each member schema authoritative for its own fields, lifecycle, claims, completion, predicates, conditions, and effects.
- Define explicit Process boundary/interface exposure and binding semantics. Scope-crossing relations/requirements may support candidate inputs/outputs, but canonical interface roles must be deliberately qualified/exposed by the Process contract; graph topology or unsatisfied holes alone must not infer normative input/output truth.
- Preserve existing authority for cardinality, conditions, target classification, lifecycle/Parent effects, relation effects, target creation/generation, and other Transition Definition or Relation semantics. Reference/reuse those contracts rather than duplicating their vocabularies inside Process.
- Define the reusable contract/binding boundary so later uses may bind different concrete artifacts/values/destinations/conditions while remaining instances of the same Process contract when the exposed contract and referenced member contracts are satisfied. Do not create a `Process Run` schema unless new independently valuable run semantics survive a separate semantic review; current Task authority does not warrant it.
- Define extraction/recognition provenance as specific typed non-parent provenance distinct from canonical Process meaning and Root Parent. Reuse Relation/Derivation/Evidence authority as appropriate; mint new Process vocabulary only where the accepted Process boundary genuinely requires it.
- Preserve human-first readability and state explicitly that Viewer/runtime graph representations are projections of the same durable Process/member/relation truth, not alternate semantic owners or justification for synthetic node classes.
- Keep measurement/calibration semantics separate. Process may reference later measurement/calibration artifacts, but this Task must not design or absorb metric/calibration representation.
- Update only canonical Tiinex/docs registry/index/semantic-package/generation or other companion material that existing schema-authoring contracts directly require for a new schema to be discoverable/valid. Do not create Site runtime projections, Viewer integrations, portable Tooling changes, or unrelated docs cleanup as part of this Task.
- Validate the authored schema and directly required companion changes with the repository's canonical/static schema validation surfaces. Preserve exact validation evidence and any limitations; do not treat successful Markdown writing alone as schema qualification.
- Return one durable Axiom result/decision plus the complete locally authored Tiinex/docs changes and validation evidence to Anchor through an independently groundable recipient-relative Handoff. No merge, push, release, or canonical publication claim is made unless separately authorized and evidenced.

## Scope

Canonical Tiinex/docs Process schema authoring and only directly required schema registration/discovery/generation companions and validation evidence. Read/recovery of current canonical docs authority is required. Out of scope: Site/Kodax implementation, Viewer UX or graph behavior, portable Loom changes, Process execution/orchestration engine, `Process Run`, Project/task/handoff redesign, measurement/calibration schema design, broad refactor parity, repository publication, merge/push, or Q product QA.
