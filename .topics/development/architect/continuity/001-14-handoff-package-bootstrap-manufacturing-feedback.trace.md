# Handoff package bootstrap and manufacturing feedback

## Observed Signal

- The current recipient-relative Handoff core can close required/reference material, correlate complete/partial workspaces, preserve exact bytes, emit closure/companion controls, reject ambiguous/stale correlation, and roundtrip packages without Site-specific semantic assumptions.
- A synthetic non-Site current-workspace pressure case can produce qualified routing and roundtrip behavior, so the package core itself is not intrinsically Site-bound.
- The operational assembly path remains caller-heavy: callers must currently construct workspace materializations/entries/completeness evidence and invoke implementation-level builders rather than one ordinary portable operation/CLI surface.
- Full Site Handoffs incidentally carry `src/tooling/portable/**` because Site is the current workspace. A Handoff whose current workspace is Docs or another repository has no equivalent standard guarantee that the portable LLM bootstrap/runtime is included and qualified recipient-relatively.
- Three distinct bootstrap concepts currently coexist and are easy to conflate: optional `tiinex.package/bootstrap.md` transport orientation; `src/tooling/portable/bootstrap/tiinex.llm.bootstrap.md` portable LLM/tooling entrypoint; and `src/tooling/portable/schema/bootstrap/**` canonical schema-material bootstrap.
- `src/tooling/portable/transfer/transfer.plan.js` describes an embedded/persistent verified bootstrap transfer direction, but current source does not expose the full described transfer package builder/verifier as an ordinary operational capability.
- The portable operation catalog/bootstrap documentation lags newer Handoff package implementation; recipient-relative Handoff manufacturing is not exposed as a normal portable operation/CLI command.
- Tooling 010 terminal return exposed package-scale pressure: roughly 1,284 workspace carriers repeatedly exhausted the old Loom process runtime during file-map/roundtrip work before recovery completed later.

## Source

- Independent Anchor review of the complete Tooling 010 return workspace and package controls.
- Focused reruns of Handoff material-closure, transport-companion, and portable aggregate tests.
- Direct source review of `materialClosure.package.js`, `handoff.plan.js`, portable bootstrap material, schema bootstrap provider material, transfer planning, and operation catalog surfaces.
- Q host/transport observation that manual LLM package assembly is a primary reliability risk and that bootstrap behavior across non-Site current workspaces is not yet clear.

## Interpretation

- Package correctness and authority boundaries are strong enough to continue dogfood, but package manufacturing is not yet sufficiently boring or discoverable to prevent LLMs from writing one-off enumeration/ZIP scripts.
- The missing capability is not more transport prose. It is a portable, workspace-agnostic manufacturing/bootstrap seam that turns qualified workspace + Handoff/context inputs into a verified recipient-relative package with explicit Tooling bootstrap policy and bounded enumeration/performance behavior.
- Bootstrap orientation, Tooling bootstrap, and schema-material bootstrap should remain semantically distinct even if one package manufacturing operation can coordinate them.

## Feedback Target

- Target: shared portable Handoff/export/bootstrap/package manufacturing surfaces under `src/tooling/portable/**`, `src/export/**`, and `tools/tiinex-portable.mjs`.

## Feedback Received

- Handoff closure and transport companion focused tests pass.
- Portable aggregate tests pass, including bootstrap startup-mode contract and runtime package roundtrip.
- These tests establish correctness of existing owners, not generic package assembly ergonomics or non-Site Tooling delivery.

## Evidence Material

- Tooling 010 return package: complete `current-site` workspace with valid closure/companion and successful recovered terminal return.
- Historical process interruption: full return package file-map/roundtrip over approximately 1,284 workspace carriers exceeded the old Loom run budget twice.
- Current Site-facing delegation: `prepareRecipientRelativeWorkspaceHandoffExport` calls shared package owner but still requires caller-supplied materialization inputs.
- Current package builder accepts arbitrary workspace ids/materializations and therefore provides a suitable shared semantic base for generalization.

## Disposition

- State: follow-up-required/open
- Follow-Up: create one bounded Loom Task for generic Handoff package manufacturing, portable Tooling bootstrap delivery across non-Site current workspaces, deterministic completeness-evidenced enumeration, ordinary portable/CLI discoverability, and package-scale hardening.
- Acceptance Effect: does not block Tooling 010 Party Role acceptance; does block any claim that cross-workspace cold-start Handoff manufacturing is fully standardized.

## Limits

- This feedback does not prescribe one archive layout, require every package to embed the full Site repository, or collapse distinct bootstrap semantics into one artifact.
- It does not require Q to debug package topology or enumerate files manually.
- It does not claim the existing package core is Site-specific; the gap is manufacturing/bootstrap distribution and operational scaling around a largely generic core.
