# Process artifact scope composition semantic classification

## Objective

Independently recover current canonical Tiinex schema/relationship authority relevant to reusable Process semantics and classify the preserved candidate that a Process is primarily a qualified reusable scope/composition over real Tiinex artifacts and their existing relations. Determine the semantic status of scope membership, boundary-derived inputs/outputs, reuse/instantiation, extraction provenance and human/graph projection without duplicating Task, Transition, Handoff, Reference, Relation or runtime semantics.

## Done Criteria

- Recover exact current published authority before inventing. Inspect the canonical Root and the nearest relevant Task, Transition, Handoff, Reference/Relation and any existing workflow/process-like schema/material at pinned source identities; distinguish current authority from Site-local feedback and historical experiments.
- Classify the core candidate explicitly as one of: existing semantics already sufficient; a new canonical Process artifact/schema is semantically warranted; Process should remain a non-schema composition/pattern; or current evidence is insufficient. Preserve the evidence and tradeoffs for the chosen disposition.
- Resolve whether a Process scope may contain/refer to genuine Tiinex artifacts and qualified relations directly, rather than defining synthetic runtime-only node types that restate those artifacts. If not, identify the exact semantic conflict.
- Resolve the boundary model: whether unsatisfied qualified relations/requirements crossing into the scoped composition can define process inputs, and whether qualified relations/results crossing out can define outputs. State cardinality/qualification implications only where current authority supports them; do not guess execution mechanics.
- Resolve reuse/instantiation semantics at the contract level: what remains invariant between observed/extracted executions and later reuse, what concrete bindings may vary, and whether equivalent outcome means contract satisfaction rather than byte/value identity.
- Classify provenance for a Process extracted from real work: whether and how it may point to the concrete source lineage segment/pattern from which it was recognized, while keeping that provenance distinct from canonical process meaning and from Parent semantics.
- Preserve human-first readability: determine whether a Viewer graph should be understood as a projection of the same real artifact/relation semantics rather than a second semantic authority. Do not design Viewer UI in this task.
- Keep the separate measurement/calibration semantic gap separate. It may be cited as neighboring pressure showing why generic Evidence/Topic should not become an untyped metric store, but do not combine metric/calibration schema design into this Process classification unless a proven canonical dependency makes separation impossible.
- Return one durable Axiom semantic result/decision with exact authority references and an explicit next boundary: no schema change; a separately scoped Tiinex/docs schema-authoring task; or a concrete blocker/unknown. Do not mutate Site runtime/Viewer/portable Tooling as part of semantic classification.

## Scope

Canonical semantic recovery and classification for reusable Process scope/composition, boundary inputs/outputs, lineage extraction provenance and reuse contract. Read-only inspection of relevant published canonical docs is allowed/expected. Out of scope: Site/Kodax implementation, Viewer UX, portable Loom implementation, Process execution engine design, generalized workflow orchestration, measurement/calibration schema design, broad refactor parity work, publication acts, or Q technical reconstruction.
