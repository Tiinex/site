# Successor Architect continuity

## Objective

Materialize an explicit Architect→Architect successor continuity Handoff before host conversation limits can erase the current role’s operational context, using current artifacts rather than a large emergency prompt as the recovery mechanism.

## Done Criteria

- Successor Handoff names exact Required Context and Reference Context for role, operating model, macro-roadmap, current gate, open debt, current Task lineage, and cold-start objective.\n- Current work ownership and retained responsibilities are explicit; historical evidence is not promoted into current authority.\n- Handoff remains understandable in a fresh empty project with template-only routing.\n- A branch-death recovery path identifies the exact current workspace/transport material needed to resume without relying on the predecessor chat.\n- Successor continuity is created early enough to be independently reviewed before the predecessor conversation is near terminal failure.

## Scope

Architect succession only. Do not transfer Tooling/Schemer/Dev work ownership implicitly, create acceptance state by transport, or make package membership semantic authority.

## Dependencies

Architect continuity spine, macro-roadmap recovery, current project state, Handoff semantics, and materially sufficient recipient transport.
