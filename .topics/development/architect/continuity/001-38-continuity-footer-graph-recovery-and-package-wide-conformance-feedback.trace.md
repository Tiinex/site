# Continuity footer graph recovery and package-wide conformance feedback

## Observed Signal

- Operator review of Continuity Integrity footers highlighted that Parent-bearing Tiinex artifacts are expected to carry a c14n-v2 Parent-target entry as well as the primary self entry.
- The requirement applies to Tiinex artifacts anywhere in a Handoff package, not only artifacts inside ordinary Workspace material.
- The same digest relation provides path-independent recovery value: a child Parent-target digest can be paired with a candidate Parent self digest even when filesystem paths or archive layout are unavailable, including manual paper-only sorting.
- The operator explicitly separated manual footer pairing from normal Tooling qualification: machine tooling should recompute and verify the relevant c14n-v2 digests rather than trusting stored footer equality.

## Source

- Current Anchor/Sigma dogfood conversation during preparation and observation of the Loom 022 Handoff route.
- Existing accepted Tooling 019 prospective Parent-target emission/validation and Tooling 020/021 inspection/repair foundation.
- Direct human/operator continuity-recovery reasoning, including pathless and printed-artifact scenarios.

## Interpretation

- Parent-target c14n-v2 is simultaneously a representation-integrity binding and a durable graph-recovery edge.
- Recovery/discovery and qualification are distinct: stored digest relationships can locate or pair candidates, while qualified machine truth requires independent recomputation against exact candidate bytes.
- Package manufacture is a carrier concern, not a separate Tiinex artifact semantics domain; the same continuity rules apply to every Tiinex artifact the carrier generates.
- Existing Tooling 019/020/021 already owns prospective emission and repair mechanics, so follow-up should extend conformance/qualification coverage rather than duplicate the integrity engine.

## Feedback Target

- Tooling 019 prospective Parent-target c14n-v2 emission and validation.
- Tooling 020/021 inspection, repair planning and bounded repair application for existing lineage.
- Handoff/package manufacture, Pointer, Workspace, bootstrap/cache descriptors and any other Tiinex Markdown artifact carried or generated by a transport, regardless of whether the artifact lives inside an ordinary Workspace tree.
- Future integrity qualification and graph-recovery fixtures.

## Feedback Received

- A Tiinex Markdown artifact that declares a qualified Root `Parent` should carry the maintained c14n-v2 continuity pair: exactly the required non-self Parent-target entry for the exact Parent representation plus the artifact's primary `Towards: self` entry. A no-Parent/root artifact must not invent a Parent target merely to produce two entries.
- Package location is not a semantic exception. Newly generated Tiinex artifacts at a carrier root, inside a Handoff route, in Workspace material, or in future bootstrap/cache/control surfaces must obey the same continuity contracts as every other Tiinex artifact.
- Exact canonical Tiinex artifacts merely carried by a package should retain their exact bytes. Transport alone is not authority to reseal, normalize, or rewrite an already materialized artifact.
- The Parent-target `Value` is useful as a path-independent graph edge. If filenames, directories, repository paths or archive layout are destroyed, a child target digest can still be paired with another artifact's primary self digest. This remains useful even for printed artifacts where a human has only the readable footers available and wants to sort papers into likely lineage relationships.
- Stored footer equality is recovery/discovery evidence, not machine qualification. Tooling must independently recompute the maintained c14n-v2 digest for the exact candidate Parent representation, verify the Parent's primary self entry, verify the child's primary self entry, and compare the recomputed Parent digest with the child's declared Parent-target value. Stale, copied, corrupt, ambiguous or mismatching footer text must fail qualification rather than being trusted because two stored strings happen to match.
- Human paper-only recovery may use `child Parent-target Value == candidate Parent self Value` as a practical pairing heuristic when no machine or power is available. That convenience must not weaken the normal machine path when computation is available.
- Pathing lineage and Parent lineage remain separate. Digest matching may locate a candidate representation but must not derive or rewrite Parent semantics from filenames, dimensions, chronology, repository adjacency or package position.
- Tooling 019 already owns prospective Parent-target emission/validation and Tooling 020/021 already own existing-lineage inspection/repair. The previously floated Tooling 028 must not duplicate those engines. If retained, 028 should be narrowed to package-wide conformance, graph-recovery qualification and regression coverage around the already accepted integrity core.

## Disposition

- State: accepted-for-planning
- Treat Parent-target c14n-v2 as both an integrity binding and a recoverable graph edge while preserving the distinction between discovery and qualification.
- Add transport-wide conformance coverage so every newly generated Tiinex artifact is checked under its real continuity declaration before a Handoff/package is considered qualified.
- Add path-independent fixtures that remove or scramble path metadata while retaining exact artifact bytes and prove the graph can be discovered through target/self digest relationships, followed by independent recomputation before qualification.
- Add negative fixtures where stored child/Parent footer strings agree but independently recomputed candidate bytes do not, proving that stored equality alone never qualifies the edge.
- Reconcile the deferred Tooling 028 wording from the current Loom 022 route against accepted Tooling 019/020/021 instead of opening a second creation/repair implementation.

## Limits

- This feedback does not authorize rewriting published history or opportunistically repairing carried canonical artifacts.
- It does not make checksum equality semantic Parent authority, publication evidence, Origin evidence or proof that a candidate was the intended Parent.
- It does not treat OCR/text extraction of a printed artifact as exact-byte cryptographic qualification unless an explicit future representation contract makes that claim possible.
- It does not require two v2 entries for artifacts that truthfully have no Parent.
- It does not create a package-only integrity dialect or permit Viewer, CLI, LLM or Chrome adapters to fork the maintained integrity algorithm.
