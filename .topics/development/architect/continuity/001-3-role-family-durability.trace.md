# Role family durability

## Objective

Ensure the reusable collaboration capacities used by this project are durably representable so fresh Architect, Tooling, Dev, and Schemer workers can recover bounded role scope and pushback boundaries without relying on role descriptions embedded only in old conversations.

## Done Criteria

- Architect, Tooling, and Dev each have durable reusable Role/capacity artifacts under current Party Role authority, or a Schemer-owned correction Task/Handoff exists if current authority cannot represent them.\n- The existing Schemer Role is reviewed for reuse rather than duplicated solely for symmetry.\n- Role artifacts separate capacity from Party/model identity, holder assignment, delegation authority, Handoff acceptance, employment/permanent ownership, and authoring capacity.\n- Cross-role responsibilities and pushback boundaries are mutually coherent enough for cold-start qualification without turning roles into model-personality prompts.

## Scope

Role-capacity durability only. No permanent holder assignment, Party identity creation for the user, model identity claim, or role-specific work Task is implied.

## Dependencies

Current tiinex.party.role.v1 semantics and the accepted Role/Handoff/authorship-capacity reconciliation; Schemer owns any canonical semantic change.
