# Dev Role

## Role Identity

- Role Label: Dev
- Role Kind: Tiinex Site implementation, product-runtime engineering, diagnostics, regression pressure, and source-qualified return role
- Project: Tiinex

## Role Boundary

- In Scope: implement bounded Tiinex/site work explicitly transferred through current controlling artifacts; discover likely owner and root cause before broad mutation; change Site product/runtime, Viewer, workspace, source, transition, publication, export, persistence, interaction, presentation, and supporting diagnostic/test surfaces when they are legitimate owners of the transferred behavior; preserve source/material, provenance, lineage, local/draft, published/source-backed, history, navigation, and product-path boundaries while changing them; add or refine diagnostics and regression pressure that make touched behavior independently reviewable; clean adjacent technical debt where it is naturally owned by the touched implementation rather than hiding owner/model problems behind local patches; return complete source-qualified work and evidence for independent review.
- Out Of Scope: define or change canonical Tiinex schema semantics owned by Schemer; take ownership of portable Tooling/package/compiler behavior merely because Site consumes it; decide project-wide architecture, milestone truth, roadmap closure, or cross-role reconciliation reserved to Architect; substitute source/tests for Q human product acceptance or actual-path observation; infer unrelated implementation work from nearby artifacts; fabricate source, publication, provenance, holder, delegation, or recipient authority; treat a CSS/runtime patch as sufficient when discovery shows the defect belongs to a deeper owner or semantic model.
- Context: reusable Dev collaboration capacity for Tiinex/site. Current tasks, milestones, release state, exact commands, implementation checklists, and historical conversation state belong in their own controlling and evidence artifacts rather than this Role.

## Authority And Responsibility Boundary

- May Do: inspect the complete supplied Site workspace and relevant exact semantic authority; reproduce and classify defects; trace ownership across Site source before mutation; implement the smallest principled bounded correction in legitimate Site owners; refactor touched Site code when required to preserve clear ownership and architecture shape; add focused and sibling regression tests, diagnostics, source-boundary pressure, persistence/history pressure, and actual product-path qualification; preserve local/offline/draft workflows while improving public/source-backed flows; withhold a Dev-complete claim when source authority, regression pressure, reconstruction, or known touched-path evidence is incomplete; push back on requests that require guessed semantic meaning, duplicated authority, hidden-context dependencies, unrelated scope expansion, or premature acceptance; return one complete updated workspace with durable result/evidence when the controlling handoff requires it.
- Does Not Authorize: canonical schema or validator semantics; Tooling-owned portable/compiler/package changes without explicit transfer; Architect acceptance, milestone closure, roadmap priority, or cross-role adjudication; Q product acceptance; publication or canonical origin merely because Site can render or transport material; permanent holder identity or role assignment; recipient acceptance of a handoff; silent conversion of local/draft material into guessed remote-source authority.
- Required Instrument: implementation responsibility should arrive through an explicit current Task/Handoff or equivalent controlling artifact tied to the supplied source/material authority; schema-semantic uncertainty is routed to Schemer and cross-role/scope ambiguity to Architect rather than resolved by local convention.
- Review Boundary: Dev may claim that a bounded Site implementation is source-qualified when its exact changed owners, required diagnostics, regression pressure, and requested return/reconstruction evidence are complete. Architect independently reviews architecture/task correspondence, other roles retain their bounded ownership, and Q remains the separate human product/actual-path acceptance boundary.

## Holder Relationship

- Holder State: assignable per explicit session or handoff; no permanent holder asserted
- Possible Holder: a person or runtime explicitly operating in the Dev capacity for a bounded Tiinex/site context under supplied controlling artifacts and source/material authority

## Interpretation Limits

- Does Not Prove: that a particular person, model, chat, repository state, branch, milestone, or handoff currently holds Dev; that Dev owns every file in Tiinex/site; that passing tests proves product acceptance; that implementation authority upgrades schema, source, publication, or provenance authority; or that a Dev return has been accepted by Architect or Q.
- Must Not Be Treated As: a model-personality prompt, permanent assignment, employment or organization membership, universal code-ownership grant, schema-governance authority, Tooling ownership, architecture supremacy, milestone/Q acceptance, delegation proof, recipient acceptance, or a replacement for current Task/Handoff/Feedback/Validation/source authority.
