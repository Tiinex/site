# Tooling 026 — cold-start Tiinex-first ingress and preferred-path qualification

## Objective

Make cold-start efficiency and predictability mechanically testable: when Tiinex Tooling is available, a fresh consumer should enter through qualified Tiinex orientation/discovery, ground its recipient Role and current interaction before substantive reasoning, and bind host/provider differences through provider-neutral capabilities rather than arbitrary artifact archaeology or provider-specific semantic forks.

## Done Criteria

- Define an explicit cold-start ingress contract that distinguishes qualified Tiinex-first orientation/discovery from native fallback and records why fallback was required.
- Preserve the hard boundary that a consumer with no signal Tiinex exists may require one minimal host/bootstrap ingress action; do not pretend package bytes can invoke Tooling before the host/consumer knows the Tooling entrypoint exists.
- Add measurable qualification evidence for routed Handoff cold-start and workspace-with-bootstrap cold-start: native actions before Tiinex takeover, arbitrary files read before orientation/frontier, calls/bytes/time to orientation, candidate artifacts inspected and fallback use.
- Add an observed Axiom-style fixture or equivalent where broad native ZIP/filesystem/Python archaeology eventually reaches the correct answer; prove that this is recovery evidence but not preferred-path PASS when qualified Tiinex orientation/discovery was available.
- Require recipient Role grounding before substantive work where Role material is resolvable: record current Role artifact/transition/predecessor grounding state, exact boundary loaded and Handoff/Role compatibility. Missing current Role material may degrade grounding without automatically invalidating a bounded `To Kind: role` endpoint.
- Ground interaction participants/contributions without assuming one transport channel equals one semantic human identity. Support multiple declared speakers/identities and multiple Roles/capacities, preserving unknown/unverified attribution explicitly.
- Ground interaction purpose/mode without assuming every Handoff is one-shot execution/return. Fixtures must include at least one non-execution mode such as design discussion, explanation or review where continuing dialogue is correct behavior.
- Define a degraded capture path for environments such as voice/STT where Tooling is unavailable: preserve contribution/speaker attribution, prohibit Tooling-dependent mutation/claims and require later Tooling-capable condensation/qualification for durable artifacts.
- Reuse `orient-handoff-package`, `search-lineage`, `discover-tooling`, `plan-host-action` and accepted receipt/capability boundaries where applicable rather than inventing parallel discovery/trust models.
- Define provider-neutral operation capability requirements and distinguish provider, host and current session capability instance. Provider name alone must not grant capability or authority.
- Define a non-authoritative host projection contract suitable for bootstrap guidance and future host-specific skill/instruction formats. Projection content must be traceable to canonical schemas/operation contracts/capability bindings and must not introduce unexplained semantic rules.
- Keep capability advertisement separate from exercised capability evidence. Trust-sensitive operations continue to require accepted exact receipts where their existing contracts demand them.
- Preserve explicit unavailable/degraded paths. Missing capabilities must not trigger improvised hidden network access, repository authority, remote writes, authentication or fabricated receipts.
- Keep `lineage leaf`, workflow/current frontier and Task state semantically distinct. This task may define the preferred discovery interface needed to expose them, but must not collapse them into one boolean.
- Add cold-start fixtures runnable by a fresh consumer with no prior conversation history and bounded bootstrap input; record whether the preferred path was followed, not merely whether the final answer was correct.
- Leave zero-state empty-workspace/starter-template qualification as an explicit later extension unless bounded implementation can prove it without widening this task.

## Scope

Portable cold-start orientation/discovery ingress contract, observable qualification metrics/receipts, Role/participant/interaction consumer grounding, provider-neutral capability requirement/binding projection and focused cold-consumer fixtures.

Out of scope: new canonical Skill schema, provider-specific semantic forks, carrier workspace-archive representation changes, Viewer/VS Code UI implementation, remote provider authentication/write, Tooling 021 repair apply, zero-state starter authoring itself or replacing canonical Handoff/Schema/Process authority.
