# Tooling 027-5-22 — minimal fresh Workspace bootstrap sufficiency qualification

## Objective

Prove or falsify that a genuinely blank LLM can bootstrap into Tiinex and accept one bounded Handoff from a deliberately minimal Workspace materialization without relying on the accidental history, Role tree, Tooling 027 lineage, or familiar repository structure of `tiinex-site`.

## Done Criteria

- Use a genuinely blank/fresh LLM dialogue with no prior Tiinex, Anchor, Loom, Axiom, Kodax, or Tooling 027 conversation state.
- Manufacture the package using the accepted recipient-v2 carrier and embedded portable bootstrap.
- The test Workspace materialization contains exactly one ordinary Tiinex work artifact and one Tiinex Handoff artifact as work/context payload.
- Durable Workspace identity/representation required by the carrier is permitted as transport mechanics and is not treated as an additional work artifact.
- No mature `tiinex-site` `.topics` tree, historical Tooling tasks, recipient Role artifact, unrelated source tree, or extra semantic context is carried into the minimal Workspace merely to help the recipient.
- The one work artifact contains all domain content needed by the one Handoff; the Handoff explicitly references that artifact as Required Context or controlling material as appropriate.
- Outer transport text is generated by Tooling from package truth and contains only the standardized common Start plus the exact recipient-specific Continue-from Pointer.
- Recipient begins at the named Start, resolves the addressed Handoff through package artifacts, uses the embedded bootstrap when needed, and identifies the single work artifact without user clarification.
- Recipient can state the bounded transferred work and what artifact is authoritative without inventing missing Workspace history.
- Any inability to resolve the Handoff, request for unexplained repository context, broad speculative archaeology, bootstrap ambiguity, or dependency on hidden prior knowledge is recorded as a qualification finding.
- Test is read-only from the recipient perspective; no source mutation or follow-up implementation is required for PASS.
- Anchor preserves exact package identity, exact transport text, recipient response, and PASS/FAIL classification before using the result as evidence for cold-start Anchor succession.

## Scope

Synthetic minimal-carrier qualification only. The purpose is bootstrap sufficiency, not realistic repository-scale work, role succession, or transport precedence under stale warm context.

## Interpretation Boundary

A PASS proves that the tested bootstrap + recipient-v2 package can carry one minimal Tiinex work boundary into a blank recipient. It does not prove warm-context precedence, mature Workspace scale, multi-role succession, or that a fresh Anchor can yet replace the current Anchor dialogue.
