# Tooling 026 Anchor acceptance

## Decision

- State: accepted-bounded
- Subject: Tooling 026 cold-start Tiinex-first ingress and preferred-path qualification
- Decision: accept the shared portable cold-start qualification implementation, recovery-versus-preferred distinction, recipient/participant/interaction grounding, provider-host-session capability projection, degraded capture boundary, and additive preferred-path START guidance as the implementation baseline.
- Boundary: acceptance covers portable semantics and deterministic qualification mechanics only. It does not claim the current carrier layout is solved, does not turn recovery into preferred-path evidence, does not authorize remote/authenticated mutation, and does not replace later real cold-start qualification.

## Basis

- The Loom-to-Anchor return carrier orients `ready` with one qualified Loom-to-Anchor route, all 2/2 Required Context items qualified, and package-context audit coverage `435/435` with zero unexplained carriers.
- Independent replay passes `coldStartQualification.test.mjs`, host capability discovery, concrete tool bindings/host action planning, bootstrap, Pointer, normal human-output, context-audit, Handoff manufacture, operation catalog, and TypeScript typecheck.
- Source review confirms routed Handoff ingress expects `orient-handoff-package` as the first semantic operation after at most one minimal host/bootstrap action; workspace ingress expects `discover-tooling` then `search-lineage`; arbitrary native archaeology before qualified takeover prevents preferred-path PASS even when recovery later succeeds.
- Recovery state and preferred-path state remain distinct. The deterministic broad-native-archaeology fixture is classified `recovered-not-preferred`.
- Recipient Role grounding is explicit and may degrade when current Role material is unavailable rather than fabricating identity or authority. Participant identity is not inferred from one transport channel.
- Provider, host, and current session capability instance remain distinct; provider naming and capability advertisement do not create exercised authority.
- Degraded Tooling-unavailable capture preserves attribution while prohibiting Tooling-dependent durable claims/mutation until later qualification.
- Broader aggregate/architecture/schema-binding checks that require source files omitted from the carried snapshot remain unavailable rather than being converted into claimed passes.

## Consequences

- Tooling 026 may now be consumed by Tooling 027 carrier/control-plane work and later adapters without creating a second trust/discovery model.
- Actual cold-start qualification must score the path taken, not only answer correctness.
- The current returned package still uses the existing `tiinex.package/*` carrier/control structure; it is not the new recipient-relative carrier format reserved for personal Sigma inspection.
- Observed execution/UX durations are now preserved separately in `001-39-observed-execution-and-ux-timing-preservation.trace.md`; they are factual preserved material, not yet a benchmark or estimation claim.
- Tooling 027 remains the next active carrier audit/representation tranche.

## Limits

- No Viewer/VS Code product integration is accepted here.
- No zero-state starter authoring is claimed solved.
- No remote write, authentication execution, Git mutation, commit, push, or publication is authorized.
- No carrier-format migration is accepted by implication.
- No host `Worked for` duration is treated as equivalent to end-to-end wall-clock without explicit downstream measurement assumptions.
