# Tooling 027-3 — Handoff route-artifact conformance and ready-gate correction

## Objective

Make `manufacture-handoff-package` and the shared Handoff orientation/readiness path refuse a `ready` package when the selected semantic Handoff artifact fails its declared Root/schema contract, while preserving exact carried bytes and keeping the Tooling 027 carrier-format/Axiom question unchanged. Use the current invalid 027 return as a regression fixture: cryptographic self/Parent-target equality is necessary but must never substitute for schema/continuity qualification.

## Done Criteria

- Add one shared selected-Handoff conformance gate consumed by manufacture and package orientation/readiness rather than duplicating schema rules in adapters.
- The gate must validate the exact selected Handoff bytes against the declared registered `tiinex.handoff.v1` contract plus Root continuity/integrity before a package can report `ready`. At minimum fail closed on missing required sections, closed-domain field violations, malformed/missing required Parent Origin authority, self-integrity failure, and required Parent-target integrity failure.
- Preserve the distinction in `001-38`: stored footer equality may aid recovery, but qualification recomputes/validates exact bytes and does not allow a valid checksum to mask an invalid semantic/schema representation.
- Do not reseal, normalize, or silently rewrite a carried Handoff merely to make manufacture pass. Invalid supplied Tiinex artifacts remain exact evidence and must produce explicit findings/blocking state.
- Preserve package-wide conformance direction for newly generated Tiinex Markdown controls/projections: any Tiinex artifact generated by manufacture must be validated under its real declared schema/continuity contract before `ready`; exact pre-existing carried material remains immutable and is reported rather than opportunistically repaired.
- Add focused regression fixtures proving: valid selected Handoff passes; missing `## Exclusions And Dependencies` blocks; invalid `Transfer Kind` blocks; invalid `Signal Kind` blocks; Parent with missing required `browse + git` blocks; Parent-target/self strings that verify do not override schema failure; malformed self or Parent-target integrity blocks; generated Tiinex route controls are conformance-checked.
- Preserve existing Tooling 026 preferred-path, Pointer/START, context-audit, single/multi-workspace, material-closure, human-output, file-map/tamper, and manufacture-scale behavior. No current carrier representation migration belongs in 027-3.
- Produce a new Loom correction result, preferably `027-1-1-...schema-conformance-corrected-result.trace.md`, under a schema-valid body shape that preserves the substantive 027 audit findings and explicitly records this correction. Because the published Tooling 027 task is an exact qualified Parent candidate, use it only if Root Parent/Origin requirements are fully satisfied and then emit Parent-target v2 plus self v2. Do not infer Parent from numbering.
- Produce a return Handoff that validates cleanly against `tiinex.handoff.v1`: use only allowed transfer/signal domains, include `## Exclusions And Dependencies`, and do not declare a Parent to local unpublished result material unless truthful required Origin authority exists. Its footer must follow the same package-wide integrity rules.
- The corrected package must independently orient/context-audit without schema-conformance findings and must demonstrate that substituting the original invalid 027 return Handoff causes the new readiness gate to block.
- Return exact implementation/test evidence plus one normal current-format recipient Handoff package. This task does not create the future new carrier format and therefore does not trigger Sigma's first-new-format inspection gate yet.

## Scope

Shared Handoff selected-route conformance qualification, manufacture/orientation ready gating, focused generated-Tiinex-route control checks, regression fixtures, and schema-valid correction of the Tooling 027 audit/result return artifacts.

Out of scope: workspace↔archive semantic classification, production nested-workspace carrier migration, zero-JSON/new-format implementation, Viewer/VS Code work, publication/authentication, Git commit/push, historical lineage repair, or changing canonical Handoff/Root schemas.
