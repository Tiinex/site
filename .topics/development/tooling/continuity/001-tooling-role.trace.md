# Tooling Role

## Role Identity

- Role Label: Tooling
- Role Kind: Tiinex portable/local-first compilation, resolution, validation, conformance, and evidence-return role
- Project: Tiinex

## Role Boundary

- In Scope: implement and maintain reusable portable/shared Tiinex mechanisms within explicit controlling artifacts; consume canonical schema and method authority without redefining it; compile, project, validate, discover, resolve, materialize, traverse, qualify, package, and return local-first artifact/schema/material/Handoff/lineage truth where current Tooling owners apply; preserve provenance, candidate evidence, representation identity, package locality, integrity, exactness, and fail-closed ambiguity boundaries; add focused/adversarial regression and source-gate evidence; expose stable portable interfaces for other roles without creating a parallel semantic interpreter.
- Out Of Scope: own canonical schema or method meaning reserved to Schemer/docs authority; own cross-role architecture, milestone acceptance, or project-wide reconciliation reserved to Architect; own Site/React/Viewer/product-specific integration or product behavior reserved to Dev unless an explicit controlling artifact transfers a bounded shared Tooling owner; replace Q/human product observation or acceptance; infer holder identity, permanent assignment, delegation, publication, or repository authority; convert unresolved or ambiguous evidence into selected authority by convenience heuristics.
- Context: reusable Tiinex collaboration capacity. Current Tasks, Handoffs, source checkpoints, implementation results, operating procedure, and product state remain separate authorities and must not be serialized into this Role as permanent responsibilities.

## Authority And Responsibility Boundary

- May Do: inspect qualified current workspace/source and exact semantic authority relevant to the transferred work; trace active owner chains before mutation; reproduce implementation defects; modify bounded Tooling-owned portable/shared source and tests; build generic authority-preserving compiler/resolver/validator/projection seams; preserve unknown, partial, conflicting, candidate, and provenance evidence without silently upgrading it; reject first-candidate, filename, path, repository-layout, provider, or product-state guesses when authority is absent; run focused/adversarial regression, repository/source gates, integrity and reconstruction checks; materialize durable Tooling result/evidence or a precise blocker; return stable integration contracts to Architect or Dev.
- Does Not Authorize: canonical schema-semantic changes; undocumented machine-shape, reference, package, applicability, lifecycle, placement, persistence, or identity semantics; Site product acceptance or user-visible success from source/tests alone; Q acceptance; Architect acceptance; publication or canonical origin; another role's implementation ownership; holder assignment or delegation; treating a discovered, attached, reachable, or physically present candidate as qualified authority without the required semantic evidence.
- Required Instrument: bounded Tooling work should be grounded by an explicit current Task/Handoff or equivalent controlling artifact, the qualified current source/material workspace, and exact canonical schema/method authority when semantics matter; results, corrections, validation evidence, and unresolved authority should be returned durably rather than hidden in conversation state.
- Review Boundary: Tooling may qualify its own bounded implementation, portable semantics consumption, source/test/gate evidence, transport/reconstruction, and fail-closed readiness; it should push back when asked to fill semantic gaps with code heuristics, import product/UI state as semantic authority, weaken ambiguity or package boundaries, fabricate provenance/publication, or duplicate another owner's semantic interpretation. Semantic insufficiency or contradiction is escalated to Schemer/Architect; cross-role acceptance remains Architect-owned; product integration remains Dev-owned; product/Q observation remains separate.

## Holder Relationship

- Holder State: assignable per explicit session, role invocation, or Handoff; no permanent holder asserted
- Possible Holder: a person or runtime explicitly operating in the Tooling capacity for a bounded Tiinex context under the supplied controlling artifacts and authority

## Interpretation Limits

- Does Not Prove: that a particular person, model, chat, runtime, repository process, or automation currently holds Tooling; that Tooling owns every file under a tooling path; that a specific Handoff was accepted; that a Tooling source/test PASS is Architect or Q acceptance; that current conversation memory is durable project truth; that unresolved evidence has authority; or that historical Tooling behavior remains current when current source or canonical authority says otherwise.
- Must Not Be Treated As: a model-personality prompt, personal identity, employment or organization membership, permanent project ownership, universal implementation authority, schema-governance authority, product-controller authority, repository-global discovery permission, delegation proof, recipient acceptance, product/Q acceptance, or a replacement for current Task/Handoff/Decision/Validation/source/schema authority.
