Du hade rätt igen: **v237 hade en browser-specifik transportbugg**, så mirror/proxy såg implementerade ut i tester men degraderade i riktig browser.

## Kört: v238 Issue transport response fix

## Rotorsak

Issue-surface-koden försökte märka native `fetch()`-responses med transport-tier genom att göra ungefär:

```js id="g4okzb"
Object.create(Response.prototype)
```

Det är fel i browsern. Native `Response.ok`, `Response.status`, `Response.json()` och `Response.text()` är brand-checkade. Så wrappern kunde göra att en lyckad proxy/mirror-fetch blev behandlad som ogiltig/unavailable.

Det förklarar varför:

```txt id="nofec5"
cache/direct typ fungerade
men mirror/proxy för issues inte gjorde det i riktig browser
```

## Fixat

```txt id="tvzxew"
1. Issue mirror/proxy wrappers använder nu plain delegating response object.
   Ingen Response.prototype-shell.

2. Följande bevaras korrekt:
   - ok
   - status
   - statusText
   - url
   - headers.get()
   - text()
   - json()
   - clone()
   - transportTier

3. Transport events för issue mirror/proxy har nu tydligare url/resource-evidens.

4. Tester använder nu native Response-objekt,
   inte bara fake enumerable response doubles.

5. Architecture guard blockerar återinförande av Response.prototype-shell.
```

## PoC-lärdom bevarad

```txt id="rpgrgd"
cache  = browser/source-material cache
mirror = hosted issue snapshot
proxy  = bounded GitHub issue API-tier
direct = explicit last resort
```

Direct ska fortfarande inte användas tyst när du trycker proxy/mirror.

## Viktig gräns

```txt id="e3wd4a"
Mirror fungerar bara om hosted issue snapshots faktiskt finns.
Om mirror-snapshot saknas ska mirror faila/degradera ärligt,
och då kan du klicka vidare till proxy/direct.
```

Proxy ska däremot nu ha en rimlig chans att fungera med riktiga browser `fetch()`-responses.
